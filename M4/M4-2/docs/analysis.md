## 1. 传感器链路

### 1.1 I2C 扫描优先于一切

上电先扫描总线，只认「有应答的地址」，而不是上来就按 0x68 发数据：

```
[I2C] found 1 device(s): 0x68
[IMU] MPU6050 init OK
```

这一步用 `mpu6050_scan_bus()` 实现，逐个地址发空包看 ACK，扫完再打印命中列表。
好处是接线错误、AD0 拉高（地址变 0x69）、模块没供电这几种情况能**一眼区分**，
不用去猜"读出来全是 0xFF 是为什么"。

### 1.2 量程与配置寄存器

| 项目 | 值 | 说明 |
|---|---|---|
| 陀螺量程 | ±250 dps | 131 LSB/(°/s) |
| 加计量程 | ±2 g | 16384 LSB/g |
| DLPF | 0x03（≈44 Hz） | 抑制电机与机架振动 |
| SMPLRT_DIV | 4 | 采样率 1 kHz/(1+4) = 200 Hz |
| 电源管理 | PWR_MGMT_1 = 0x01 | 唤醒，时钟源取 X 轴陀螺 PLL |

## 2. 姿态：互补滤波

### 2.1 为什么不用纯积分

陀螺零偏哪怕只有 1 dps，积分 60 秒就是 60° 的假转动。实测：

| 解算方式 | 60 秒末角度 | 偏差 |
|---|---|---|
| 纯陀螺积分（不补偿零偏） | **+70.29°** | 完全不可用 |
| 纯陀螺积分（扣掉估计零偏） | **−0.23°** | 可用，但仍会慢漂 |
| 互补滤波融合（τ=0.5 s） | **−0.27°** | 最优，且长期由加速度计兜底 |

表格第三行之所以能"兜底"，是因为互补滤波把加速度计当低频基准：
`α = τ/(τ+dt)`，τ=0.5 s、dt=20 ms 时 α≈0.9615，
每周期只让加速度计修正 3.85% 的残差，短时抗振动、长时不累积。

### 2.2 零偏必须是"估"出来的，不能写死

程序启动后先静止 1 秒，把这段时间的陀螺读数做平均，作为零偏：

```
[CAL] gyro bias = 1.16 dps (51 samples), init pitch = -2.5 deg
```

不同次上电实测在 **1.16 ~ 1.20 dps** 之间波动（俯仰轴），X 轴更是到 **10.4 dps**。
如果按某一次的值写死，换个温度、换块板子就会系统性偏移，
所以**零偏一律现场估计**，这也符合题目"不允许假设固定数据"的要求。

### 2.3 噪声水平

静止时加速度计解算角的标准差 **0.13°**，角度真值（水平放置）实测 **−1.9° ~ −2.21°**。
偏差约 2° 来自面包板与模块自身的安装倾角，不是算法误差——这也说明
**绝对角度需要一个水平基准**，答辩时要讲清楚这一点。

## 3. 编码器测速

### 3.1 硬件正交解码

TIM3 工作在 Encoder Mode（TI1 and TI2），A/B 两相进硬件，
计数完全由定时器完成，CPU 不用进中断：

- 正转计数加、反转计数减，**方向自动带符号**；
- CNT 是 16 位会回绕，读差值时按 `int16_t` 解释即可自动处理：
  实测 `cnt=65535 delta=-1`、`cnt=65512 delta=-25` 均正确；
- 百万级脉冲也不丢，因为不是软件采样。

### 3.2 CPR 实测标定（这一步不能抄公式）

CPR = 输出轴转一圈的计数值。用手转输出轴 10 圈，读累计增量：

```
[ENC] 首行 total=0  末行 total=19897  Delta=19897
CPR = 19897 / 10 = 1989.7 ≈ 1990
```

交叉验证：编码器规格为 11 线双相，四倍频后 44 计数/电机圈，
反推减速比 `1989.7 / 44 = 45.2`，与 25mm 减速箱常见的 1:45 吻合。
理论值 1980 与实测 1990 相差 0.5%，差异来自"手数 10 圈"的计数误差，
故代码取**实测值**，理论值仅作合理性校验：

```c
#define ENCODER_CPR  1990
```

### 3.3 转速换算与验证

```
rpm = Δ / CPR × 60 / 窗口秒数
```

实机校验（1 秒窗口）：

| 现象 | 数据 | 结论 |
|---|---|---|
| 正转 | `delta=1198 → rpm=36.12` | 与 `1198/1990×60=36.12` 完全一致 |
| 反转 | `delta=-922 → rpm=-27.80` | 符号正确 |
| 回绕 | `cnt=65535 delta=-1 → rpm=-0.03` | 回绕处理正确 |
| 累计一致 | 各帧 `delta` 之和 = `total` 增量 | 没有丢脉冲 |

### 3.4 手转时 rpm 剧烈跳变，为什么不是 bug

手动拨轮会得到 `36 → 17 → 61 → 13 → 69` 这种锯齿。原因有三层：

1. **人的输入本身不平滑**：手指是"拨一下、回手、再拨"，1 秒窗口内位移天然忽多忽少；
2. **窗口平均效应**：1 秒窗口把这一串不均匀的运动压成一个平均值，窗口边界不同结果就不同；
3. **量化**：10 ms 窗口下 1 个计数 ≈ 3 rpm，低速时量化台阶明显。

判定"不是丢脉冲"的依据是 §3.3 最后一行：**各段增量之和严格等于 total**，
如果丢脉冲，两者必然对不上。真实均匀转速要等 M4-3 闭环驱动后再看。

## 4. 失败边界（已知问题）

| 现象 | 根因 | 处理 |
|---|---|---|
| 编码器静止时 `delta` 跳 ±5~40 | PA6/PA7 浮空，输入悬空拾噪 | 线接实后为 0；另注意 PA6/PA7 **不是 5V 容忍脚**，编码器必须 3.3V 供电 |
| 第一次读 IMU 得到 `az=-0.48, pitch=-120°` | 上电瞬间手在动，1 秒零偏估计被污染 | 上电后保持静止 1 秒 |
| 串口出现大量 `U`、乱码 | 二进制 STATUS 帧被当 UTF-8 文本解码（0x55='U'、0x0A=换行） | 用 `--only-text` 或结构化解析，见 M4-4 文档 |
| 串口工具中途崩溃 `UnicodeEncodeError` | 二进制字节被解码成非 ASCII 字符，GBK 控制台编不出来 | 工具侧过滤非 ASCII 后再打印 |
| 融合角慢慢向加速度角靠拢 | 这是互补滤波的正常收敛，不是漂移 | 看长期是否发散，而不是看短期是否"变" |

## 5. 串口示波器实测曲线（任务 4）

截图：`docs/photos/vofa_rpm_wave.png`（VOFA+ 1.3.10，FireWater 协议，COM11 @115200）

### 5.1 怎么录的

VOFA+ 的 FireWater 协议只认"纯数字 + 逗号 + 换行"，行首字母（如 `CSV,`）会让整帧解析失败。
因此固件里做了一个编译期开关：

```c
#define VOFA_MODE   1    // 只输出 rpm 一路数值，并临时关闭文本日志与二进制状态帧
#define VOFA_MODE   0    // 恢复正常日志（平时用这个）
```

录制步骤：改 1 → 编译烧录 → VOFA+ 设 FireWater、1 通道、Y 轴挂 `rpm` → 手转输出轴 →
截图 → **改回 0 重新烧录**（否则 M4-4 的二进制帧不工作）。

### 5.2 曲线形态与手的动作对照

| 曲线段 | 手的动作 | 解读 |
|---|---|---|
| 平直 0 | 手停 | 转速真的是 0，不是丢数据 |
| 负向鼓包，峰值约 −40 rpm | 反向转 | 符号正确 |
| 中间回 0 后有小凹陷 | 换手/松开 | 瞬时扰动 |
| 正向鼓包，峰值约 +55 rpm | 正向转 | 幅值与手转速度相符 |

**整体形态与动作一一对应，说明测速链路是通的**——这是"能测"的证据。

### 5.3 曲线上的"毛刺"从哪来（题目要求解释的点）

| 毛刺特征 | 来源 | 判断依据 |
|---|---|---|
| 斜坡上细密锯齿，幅度约 ±3 rpm | **量化**：10 ms 窗口 1 个计数 = 3.02 rpm | 锯齿幅度恰好等于一个计数台阶 |
| 换向瞬间出现"尖坑"再回升 | **齿轮回程差 + 静摩擦**：反向要先吃掉间隙才建立转速 | 只在换向处出现，正反向都对称 |
| 鼓包不是平滑正弦 | **人的手不可能匀速** | 峰值高度不固定，每次转都不同 |
| 偶发孤立凹陷后立刻恢复 | **线材抖动**导致的瞬时接触变化 | 幅度大、持续短、无规律 |

### 5.4 关键论证：毛刺不是丢脉冲

如果是丢脉冲，特征是**整段数据丢失、曲线断层、累计值与转速对不上**；
而实测是**连续、细密、幅度等于一个计数台阶**的锯齿，且各段增量之和严格等于 `total`
（见 §3.3 最后一行）。所以毛刺来自**量化误差**，不是计数错误。

这个区分很重要：量化误差只能通过提高分辨率或延长窗口改善，
而丢脉冲是接线/时序问题，两者的处理方式完全不同。

## 6. 与 M4-3 的接口

编码器的**读取权收归电机模块**：`encoder_read_delta()` 是"读并清零"语义，
如果在 1 秒打印处和 10 ms 控制中断里各读一次，控制环就会漏掉一部分脉冲。
因此 M4-3 起，增量只在 10 ms 中断里读，`main` 通过 `motor_get_total()` 取结果。
这是多读者共享计数器最典型的坑，也是本模块与下一模块的衔接点。
