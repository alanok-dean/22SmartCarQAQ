## 2. 破坏测试 A：向下位机注入坏帧

命令：`--inject 20`（每 20 个好帧往串口写一帧 CRC 故意写错的帧）

脚本构造的坏帧：`SOF/VER/LEN/MSG/SEQ/PAYLOAD` 全部合法，仅 **CRC 高字节取反**。

```
[RX] seq= 79 ... bad=  0 | good=18
[RX] seq= 85 ... bad=  1 | good=25      ← 第 1 个坏帧被识别
[RX] seq=250 ... bad=  1 | good=190
[RX] seq=  8 ... bad=  2 | good=205     ← 第 2 个
[RX] seq= 47 ... bad=  3 | good=245     ← 第 3 个
[RX] seq= 69 ... bad=  4 | good=268     ← 第 4 个
[SUM] 好帧=305 坏帧=0 注入脏包=4
```

| 结论 | 证据 |
|---|---|
| 下位机坏帧计数准确 | `bad_frame_cnt` 0→4，与注入次数 **4** 完全一致 |
| 坏帧后能重同步 | 每次 `bad` +1 之后 `good` 继续增长，**没有一次中断** |
| CRC 覆盖范围两端一致 | 故意破坏 CRC 高字节即被判错，说明两端用同一段字节算 CRC |

## 4. 破坏测试 C：拔插 USB-TTL

运行中拔掉 TTL，等 3 秒插回：

```
[RX] seq=  0 ... hb=    0 bad=  0 | good=24 bad=1
[WARN] 串口异常: GetOverlappedResult failed (PermissionError(13, '拒绝访问。'))
       —— 设备可能已断开，等待重连
[INFO] 串口已重新连接
[RX] seq= 30 ... hb=   30 bad=  0 | good=43 bad=1
```

| 结论 | 证据 |
|---|---|
| 上位机不退出、不崩溃 | 打印 `[WARN]` 后进入重连循环 |
| 自动恢复 | `[INFO] 串口已重新连接`，随后继续正常收帧 |
| 下位机不受影响 | 重新连接后 `hb` 继续递增 |

**附带发现**：本次测试中 `hb` 曾归零（`hb=4427 → 0`）。排查后确认是 **ST-Link 的
杜邦线松动导致板子掉电复位**，不是软件缺陷。之后改为板子独立 USB 供电、
ST-Link 仅接 `GND/SWDIO/SWCLK` 后不再复现。

> 这条记录保留在这里，是因为它说明了排查方法：**先看 `hb` 是否归零**——
> 归零 = 下位机重启（供电/复位问题），不归零但 `good` 中断 = 通信问题。这是最快的分流手段。

## 5. 现象与归因

### 5.1 串口监视器满屏乱码（`U`、控制字符、随机汉字）

**现象**：用文本方式打开串口，`[HB]` 之间夹杂大量乱码，每行都带一个 `U`。

**原因**：STATUS 是二进制帧，被文本解码器按 UTF-8 解释：

- 帧内 `0x55`（SOF 第二字节）恰好是 ASCII 的 **`U`**
- 帧内 **`LEN = 0x0A`** 恰好是换行符 `\n`，于是每帧被从长度字段处**切断**成 2~3 行

**处理**：文本日志与二进制帧共用一条串口，但分析时必须分离——文本用
`serial_mon.py --only-text` 过滤，二进制用状态机解析。

### 5.2 随机字节注入时坏帧计数不增长

**现象**：早期用 5 个随机字节做注入，`bad_frame_cnt` 一直是 0。

**原因**：这是**设计如此**，不是缺陷。协议规定 `WAIT_SOF1` 状态下收到非 `0xAA` 的字节
属于**链路噪声**，静默丢弃且不计数。只有"帧头对、结构完整、CRC 错"才算坏帧。

**为什么这么设计**：否则上位机随便发一个字节、或线路抖动一次，计数就 +1，
`bad_frame_cnt` 会变成无意义的噪声计数器，无法反映真实的链路质量。

### 5.3 `seq` 跳变

打印中 `seq` 每次跳 5~8，不是逐 1 递增。原因是打印被限流到每 0.25 秒一次，
而状态帧是 20Hz，两次打印之间自然跨过了 5 帧。**不是丢帧**——总帧数与时间对得上。

## 6. 失效边界（这套方案什么时候会坏）

| 场景 | 会发生什么 | 已知的改进方向 |
|---|---|---|
| 波特率不匹配（一端 9600） | 收到的是乱字节流，帧头几乎不可能命中，表现为"完全无有效帧"，但**两端都不崩** | 加自动波特率探测，或协议层加握手协商 |
| 单帧 `LEN` 被改成 >64 | 直接丢帧 + 计数，状态机回 `WAIT_SOF1` | 已处理 |
| 连续大段脏数据 | 每丢一帧就重找帧头，恢复快；但若脏数据持续存在，会持续 `bad++` | 可加"连续 N 次失败后清空缓冲"的退避策略 |
| 主循环被耗时任务阻塞 | 50ms 状态帧周期会漂移，`seq` 不连续（但接收不受影响，因为中断独立） | 改为定时器中断驱动发送，或用 DMA |
| 上位机长时间收不到数据 | `select` 100ms 超时后空转，CPU 占用低但无告警 | 可加"连续 N 秒无有效帧"的健康度上报 |

---

## 7. 结论

- 协议两端**独立实现、逐字节对齐**：示例帧 CRC 一致，坏帧判定一致。
- 三种破坏（错波特率模式下的乱流、脏字节、拔插）下**两端均不死机**，
  坏帧计数准确，且都能自动重同步。

## 8. Linux 上位机与 MCU 的真实串口联调

前面几节的数据来自 Windows 端的 Python 工具。任务 4 要求上位机是 **Linux C 程序**，
因此又用 `upper.c` 与实板做了一次联调。

**环境**：WSL2 Ubuntu 22.04 + `usbipd-win` 把 CH340（USB-SERIAL CH340，VID:PID = 1a86:7523）
从 Windows 透传进 WSL，WSL 内出现 `/dev/ttyUSB0`。

```bash
$ usbipd list                      # Windows 侧
1-2    1a86:7523  USB-SERIAL CH340 (COM11)
$ usbipd bind --busid 1-2
$ usbipd attach --wsl --busid 1-2

$ cd M4/M4-4/linux && make && ./upper -d /dev/ttyUSB0 -s 40,40 -t 8
```

### 8.1 联调结果（M4-3 + M4-4 打通）

`CMD_SPEED` 下发后，下位机把目标转速交给 M4-3 的速度环，状态帧回传**实测轮速**：

```
[INFO] /dev/ttyUSB0 @ 115200 8N1
[TX] CMD_SPEED L=40 R=40 : AA 55 01 04 00 01 01 28 00 28 00 0F 2E
[RX] t= 0.3s seq= 21 L=   41 R=   41 pitch=  -1.6 hb=  277 bad=  0 | good=6 bad=0
[RX] t= 1.1s seq= 36 L=   39 R=   39 pitch=  -1.6 hb=  292 bad=  0 | good=21 bad=0
[RX] t= 3.0s seq= 74 L=   40 R=   40 pitch=  -1.6 hb=  330 bad=  0 | good=59 bad=0
[RX] t= 7.9s seq=173 L=   39 R=   39 pitch=  -1.6 hb=  429 bad=  0 | good=158 bad=0

[SUM] 好帧=159 坏帧=0 注入脏包=0
```

可以确认四件事：

1. **CRC 校验双向正确**：159 帧全部通过，0 坏帧；
2. **帧率准确**：`hb` 每 0.3 秒 +6，即 20 Hz，与 50 ms 周期一致；
3. **载荷是真实物理量**：`pitch=-1.6°` 来自 MPU6050，`L/R` 来自编码器闭环，
   不是写死的常量；
4. **闭环精度**：目标 40 rpm，实测稳定在 39~41 rpm（±2.5%）。

至此链路完整：

```
PC(C) --CMD_SPEED--> 协议解析 --CRC--> PI 速度环 --> TB6612 --> 电机
                                                              |
PC(C) <--STATUS---- 组帧+CRC <--实测rpm/俯仰角 <-- 编码器/MPU6050
```

### 8.2 联调中踩到的两个坑

| 现象 | 根因 | 解决 |
|---|---|---|
| WSL 里 `upper` 收到 0 帧，Windows 端却正常 | CH340 已挂在 Windows 上 | `usbipd bind + attach --wsl` |
| 烧录后串口**一个字节都没有**，`cat /dev/ttyUSB0` 抓 0 字节 | Keil 下载后默认不自动运行，芯片停在调试挂起状态 | 勾选 `Flash Download → Reset and Run`，或下载后按一下 RST |

第二个坑尤其值得记：**"串口没数据"不等于"协议写错了"**，先用
`cat /dev/ttyUSB0 | xxd` 抓原始字节，就能区分"板子没在发"和"程序解析不了"。
